Borrowed instruments arrive as metaphors unless something stops them.

Four lines of work, one method. Each borrows a mature instrument from a field that has already been rigorous about measurement, states exactly what maps to what, and names the observation that would sink it.

Method The discipline of import Three things every project carries before it is allowed to produce a result.

Machine learning borrows constantly: from information theory, from control engineering, from neuroscience, from statistics. Borrowing is not the problem. Borrowing loosely is. A tool imported as an analogy produces figures that look like evidence and are not.

Every project here carries three things before it produces a result. A contract, saying what in the borrowed theory corresponds to what in the system. A null model, saying what the instrument reports when there is nothing there. And a falsifier, a stated observation that would tell us the whole approach was wrong.

This is a slower way to publish. It is also the only version of the work we would be willing to hand to a company that has to answer for the system afterwards.

01 Interpretability What a model is doing, and when the answer is evidence.

Reading a trained system

Most interpretability results are descriptions that nobody can check. A saliency map, a feature label, a circuit diagram: each is a hypothesis about a computation, presented in a format that resists disagreement. We work on the version of the field where the description can lose.

Concretely: counterfactual explanation, where the claim is tested by changing the input and seeing whether the model moves as predicted; mechanistic analysis of internal structure, using a graph vocabulary that network neuroscience spent two decades making honest; and identifiability, the question of whether a model's report about its own reasoning is evidence about that reasoning.

It is not, on its own. What follows from that is an evaluation recommendation rather than a warning. A self-report benchmark can be made to test the thing it claims to measure: hold the named intervention fixed, shift the environment around it, and see whether the report stays bound. Most of what we do lands in that shape, as a change to how a claim is checked rather than a reason to stop making it.

02 Representation learning How the structure inside a model comes to be there.

How a network comes to encode what it encodes

A trained network ends up carrying structure that nobody put there by hand. Which structure appears is decided by an interaction between architecture, data, optimiser, scale, and increasingly the post-training stage. Most claims about that interaction are made by comparing two models that differ in several of those at once, which is why so few of them survive.

We work with designs that isolate one variable. A matched pretrained and instruction-tuned checkpoint sharing architecture, tokeniser and pretraining seed leaves the post-training step as the only thing free to vary, which is what makes a claim about that step testable at all.

The recurring question is the gap between presence and use: a capability can be cleanly decodable from a representation and still play no part in what the model actually outputs. Decodable is not the same as used, and the difference matters for anyone reading a probe result as evidence.

03 Imaging & biosignals Where an unexplained model is not an option.

Medical images and physiological signals

Clinical machine learning is where interpretability stops being an academic preference. A radiologist or a cardiologist is accountable for the decision, so a model that cannot be interrogated is a model that cannot be used, whatever its numbers say.

Our work covers counterfactual analysis of ECG for infarction detection, evaluation of saliency-based explanation in mammography, and segmentation, including a benchmarking study of how badly the field's standard practices handle small organs. Across all of it the same question: does the explanation change when the underlying decision changes, or is it decoration?

04 Language & software The applied half, and the one with the nearest industrial partners.

Language models, and the software they reshape

A language model in a company is never just a model. It is a retrieval layer, a document base that was never written to be queried this way, an evaluation story, and a set of architectural commitments that nobody consciously made.

We work on both ends. On the retrieval side: chunking, vector search and evaluation for systems that must answer from a real corpus. On the software side: how these systems change the architecture around them, including the design decisions that coding assistants and multi-step agent systems make on a team's behalf without anyone reviewing them.

Resources Compute

The work is deliberately compute-light. Small open models, national HPC allocation, and methods that a hospital or a mid-sized manufacturer could run themselves. A result that only reproduces on a frontier cluster is a result our partners cannot use.

Each line is easier to judge from what it produced than from what it claims.
